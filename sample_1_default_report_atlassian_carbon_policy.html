エグゼクティブ・サマリー

結論

標準は Claude Code。ただし完全な1本化は行わず、プロジェクト特性・役割に応じて Codex 等の併用を申請制で認める。AI業界は流動的なため標準は固定化せず、期間を区切って検証し定期的に見直す。コンテキストはソースコード側にあり、スキル／プロンプト／メモリも Markdown 形式で相互移行可能なため、ロックインの懸念は限定的。

3

方針：Claude Code を標準とする

現場の利用実感に基づく主な推奨理由は以下のとおりです。

✓コードの正確さ

正確性が重要なコード（PF運用のIaC等）で安定した品質。

✓複雑・探索的タスクへの強さ

設計・探索を伴う作業、IaC（Ansible等）、Android の設計・画面生成で明確に差が出る。

✓ドキュメント・図表生成品質

仕様書や SVG 等の図表生成で品質が高い。

✓Atlassian 連携の使い勝手

Confluence／Jira 連携でチャット面を含め現状で優位（Codex も MCP 経由で連携自体は可能）。

✓企業姿勢・長期継続性

15年続く長寿命プロダクトでは、提供元の継続性・理念の安定性も選定要素となる。

✓プラン経済性

Team Premium に Claude Code 利用枠がバンドルされ、1日の利用量に概ね収まる。

4

例外モデル：Codex を申請制で併用

なぜ完全な1本化を行わないのか、その理由と運用方針を整理します。

+局所的タスクで有効

全タスクのうち約3割は Claude Code 単独では取りこぼしがあり、その用途で Codex が有効。

+初期コーディングのたたき台

「Codex で初期コーディング → Claude Code で検証」というスタイルが機能。

+相互レビュー

片方が書いたプランをもう片方が精査・レビューする併用が現場で機能している。

+外部パートナー

外部パートナーは現状 Codex 中心。標準化に伴い段階的に整合させる。

運用方針

これらはプロジェクト／役割単位の申請制で個別付与する。標準（Claude Code）を全員に整備したうえで、必要な人・プロジェクトに Codex を追加する形を基本とする。

ロックインに関する整理

コンテキストはソースコード側にあり、スキル／プロンプト／メモリは Markdown 等で相互移行可能（CLAUDE.md / AGENTS.md は片方をメイン・もう片方を参照として共通化できる）。一部マーケットプレイス由来のスキルは片寄せ懸念があるが AI による相互変換が可能で、移行コストは小さい。

6

データガバナンス・契約要件

基本要件は入力データがモデル学習に使われないこと。以下の項目について全社情報セキュリティ方針との突合・確認をお願いします。

学習不使用基本要件

入力データがモデル学習に使われないこと。商用規約で満たせば当面は十分と整理。

ZDR要否確認

ゼロデータ保持の要否は全社情報セキュリティポリシー次第。必須なら Enterprise 相当が要件。

データレジデンシー要確認

日本データレジデンシーの要否をポリシーに照らして確認。

SSO / SCIM要確認

シングルサインオン・ユーザープロビジョニング要件の確認。

監査ログ要確認

監査ログの取得・保持要件の確認。

補足

ZDR が不要（学習不使用の規約で足りる）の場合は Team／Business クラスで運用可能。Team／Business プランの ZDR・データレジデンシー対応状況は要確認。価格・契約条件は資料に記載された範囲を超えて断定しません。

7

情報システム部門への依頼事項

本提案にあたり、情報システム部門に以下の整備・確認・決定をお願いします。

1
開発部門へ Claude Code（Team Premium 相当）席を標準整備。
2
Codex（および技術サポート向け ChatGPT チャット）を用途／役割単位で申請付与できる仕組み・予算枠の整備。
3
各ツールの規約・セキュリティ要件（学習不使用／ZDR／データレジデンシー／SSO／監査）のポリシー適合可否を確認。
4
外部パートナーのライセンス整合方針の決定（現状 Codex → 標準との整合）。
5
PM/BL・技術サポートのツール付与方針の確定（開発部門と連携）。
6
定期的な見直しサイクル（検証→方針更新）のプロセス合意。
